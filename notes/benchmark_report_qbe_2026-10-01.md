# Lox++ QBE Backend Benchmark Report — native vs JVM vs QBE, with S8 speed work

**Date:** 2026-10-01
**Repo:** `feat/qbe-s8-register-promotion` (S8, issue #461); baseline at
`5c6f5f1`
**Machine:** 12th Gen Intel Core i5-1235U (12 logical CPUs), Linux
**Container:** `loxpp-dev-qbe` (native/QBE) and `loxpp-dev-env-managed`
(JVM)
**Toolchains:** clang 18 `-O3 -DNDEBUG` · QBE 1.3 · OpenJDK 21.0.11 (G1GC,
tiered) · Jasmin

---

## 1. Purpose

Node S8 (issue #461) adds two speed changes to the QBE backend:

1. **Register promotion** for local slots that are never captured; every
   allocating or unwinding runtime call spills the live promoted locals
   back to their stack slots first ("safe points").
2. **`GET_TAG;JUMP_TABLE` fusion**: a dense enum match reads the tag as a
   word directly instead of materialising a boxed Number and converting it
   straight back.

This report measures both against the pre-S8 QBE emitter
(`QBE_NO_PROMOTE=1` / `QBE_NO_FUSE=1`), and puts QBE in the context of the
native VM and the JVM backend. It is the S8 checkpoint.

**Headline result.**

* **QBE is about 1.5× faster than the native VM** (geomean 0.68× the native
  time) and the **JVM is about 6.4× faster than native** (geomean 0.16×).
  This repeats the S7 picture: QBE removes the interpreter's dispatch but,
  with no type specialization, cannot catch HotSpot.
* **Register promotion is a small net loss on this corpus**: geomean
  `qbe/qbe-base` **1.02**, with per-program ratios between 0.98 and 1.05
  and low spreads. It does not pay for itself.
* **Uncapped promotion regresses `mandelbrot` 1.69×** (a many-local hot
  loop where the phis and longer live ranges lose to QBE's own register
  allocation). A register-pressure cap (promote only read-only slots above
  six candidates per function) removes that regression: capped 3.9 ms vs
  base 4.0 ms. The report keeps the cap.
* **`GET_TAG;JUMP_TABLE` fusion is not measurable in time** on the
  5,000,000-iteration `examples/bench_jump_table.lox` microbenchmark (fused
  1.562 s vs unfused 1.564 s, best of five). The instruction-count win is
  real; it is simply too small for the surrounding call and arm body to
  show here.

## 2. Method

* **Suite:** 18 programs from *Are We Fast Yet?* and the Computer Language
  Benchmarks Game (`benchmarks/core/`), generated by
  `benchmarks/generate.py` with the same self-timing harness the earlier
  report used.
* **Runner:** `benchmarks/run.py`; every (program, backend) pair runs
  `--procs` times pinned to one CPU, the fastest launch is kept, and the
  median of the timed batches after dropping the first third is reported.
  `BENCH_CPU` pins to a non-default CPU.
* **Backends:**
  | backend | how a program runs |
  |---|---|
  | `native` | `build/loxpp` |
  | `jvm` | `tools/loxpp_jvm.sh` (HotSpot) |
  | `qbe-base` | `QBE_NO_PROMOTE=1 tools/loxpp_qbe.sh` — S8 fusion on, promotion off |
  | `qbe` | `tools/loxpp_qbe.sh` — S8 fusion + promotion on |
* `clock()` is process CPU time on native/QBE and wall-clock on the JVM.
* Checksums from every backend that produced one agreed on every row.
* **Caveat on an earlier attempt.** The first full run was taken while the
  host was saturated by twelve unrelated processes at ~99% CPU each; the
  numbers were unusable (native `mandelbrot` 95 ms, spreads to 200%). That
  data is discarded. Every figure in §3 is from a run on a quiet host
  (load average ~1), and the program pins one CPU.

### 3.2 Register promotion: neutral, and a many-local trap

Per-program `s8/base` runs from 0.98 (`fib`) to 1.05 (`bounce`); the
geomean is 1.019. Promotion never wins clearly and loses a few percent on
several numeric and call-heavy programs. That is the whole effect: with
the fused-stack model the baseline's loads and stores are L1-resident, and
QBE already forwards most of them, so putting locals in SSA values buys
little and costs a phi at every merge plus a spill of every live local at
every allocating call.

The trap is `mandelbrot`. Its inner loop has ~11 candidate locals; the
uncapped promoted build emits 339 local stores vs 123 in the baseline and
runs **1.69× slower** (6.6 ms vs 3.9 ms, best of ten, spread ≤ 4%) because
QBE's register allocator cannot keep them all live and spills them anyway.
The shipped **register-pressure cap** promotes only read-only slots in a
function with more than six candidates: no phi is needed for a single
dominating definition and a read-only slot's stack cell never goes stale.
With the cap, `mandelbrot` is 3.9 ms vs 4.0 ms and the corpus is as in
§3.1.

### 3.3 `GET_TAG;JUMP_TABLE` fusion

`examples/bench_jump_table.lox` is 5,000,000 iterations of a dense 5-arm
enum match. Best of five pinned runs, quiet host:

| build | time |
|---|--:|
| fused (S8) | 1.562 s |
| unfused (`QBE_NO_FUSE=1`) | 1.564 s |

The fused `.ssa` replaces `rt_op_get_tag` (which stores a boxed Number at
the tag cell) and the JUMP_TABLE's `loadl` / `d cast` / `dtosi` with one
`rt_get_tag_word` call returning the tag as a word directly. That is four
fewer instructions per dispatch, but 0.1% of a 5,000,000-iteration run:
below the noise floor, and dominated by the surrounding call and arm body.

## 4. Analysis

**QBE vs the other backends.** QBE beats the native interpreter by ~1.5×
overall, concentrated in numeric and byte-scanning code (`mandelbrot`
0.12×, `sieve` 0.30×, `spectral_norm` 0.46×, `fannkuch` 0.43×) and much
narrower on object/polymorphic-dispatch code (`richards` 1.11×, i.e. QBE
is *slower* than native there). The JVM is far ahead everywhere (geomean
0.16× native). These are the S7 conclusions, unchanged by S8.

**Why promotion is not a win.** In this backend every value already lives
in an addressable stack cell; the cost of a local access is an L1 load or
store that QBE can often forward. Promotion trades that for SSA values
whose live ranges now cross basic blocks and calls, which adds a phi at
every merge and forces a spill of every live promoted local before every
allocating call. On loop-bound code the two roughly cancel; on call-heavy
code (`bounce`, `list`) the spills are a small straight loss.

**Why the cap.** A read-only slot has one definition that dominates all
its uses: no phi, and its stack cell is never stale, so the GC sees it
without a spill. Restricting promotion to those slots in a high-pressure
function keeps the cheap part and drops the expensive part.

---

## 5. Conclusion

* Ship the `GET_TAG;JUMP_TABLE` fusion: free, correctness-neutral, and the
  right shape even if this microbenchmark cannot resolve it.
* Ship register promotion with the pressure cap. It is correctness-safe
  under `LOXPP_STRESS_GC=1` (the whole probe and example corpora pass), but
  on this corpus it is a **~2% net loss** and does not justify itself.
* **Follow-up (file as an issue):** spill only the promoted slots live
  *across* a call instead of every in-scope slot. That removes the
  `bounce`/`list` regression and is the change most likely to make
  promotion an actual win on loop-bound code. Until then, if a strict
  no-regression bar applies, register promotion should be made opt-in
  (`--promote`), leaving it off by default.

## 6. Reproducing

```bash
# dev-qbe container, worktree mounted at /workspace
cmake --preset release && cmake --build build \
    --target loxpp qbe_emit_program loxrt -j"$(nproc)"

python3 benchmarks/generate.py
python3 benchmarks/run.py \
    --backends native qbe qbe-base --procs 5 \
    --json benchmarks/results/run_s8.json

# JVM reference (dev-managed container)
cmake -S . -B build-jvm -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
    -DLOXPP_JVM_BACKEND=ON -DLOXPP_BUILD_TESTS=OFF
cmake --build build-jvm --target loxpp -j"$(nproc)"
tools/build_lox_rt.sh
LOXPP_BIN=$PWD/build-jvm/loxpp python3 benchmarks/run.py \
    --backends jvm --procs 3 --json benchmarks/results/run_jvm_s8.json

# S8 correctness gate (promotion under stress GC)
tools/check_qbe_s8_promotion.sh
```

Raw data: `benchmarks/results/baseline_qbe_2026-10-01.json` (native, QBE
base, QBE S8) and `benchmarks/results/baseline_qbe_jvm_2026-10-01.json`
(JVM).
